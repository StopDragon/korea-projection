# G70 실차 검증 기록과 미해결 사항

검증일: 2026-11-21, 한국 시간. 차량 소유자가 실제 화면 연결을 확인한 보조 패키지는 **0.4.0**입니다. 이 PR의 0.4.1은 저장소 통합과 추가 USB 선택 검사를 포함한 개발판입니다.

## 확인한 동작

동일한 2022 G70/펌웨어에서 초기에는 Wi-Fi 부품 없음으로 모드 설치가 생략됐습니다. 검증한 드라이버를 동글 연결보다 먼저 등록하고 인터페이스·존재 표시를 제공하자 KP 자체 검증을 거쳐 모드가 설치·적용됐습니다. 단독 AP 시험에서는 5 GHz AP와 DHCP 임대를 확인했고, 0.4.0에서는 실제 CarPlay 화면 연결이 동작했다고 차량 소유자가 확인했습니다.

0.4.0의 최신 저장 시점은 부팅 약 385초 뒤입니다. 아래는 공개 가능한 상태와 집계만 옮긴 것으로, 원본 사용자 기록을 저장소에 넣지 않았습니다.

| 항목 | 관측 |
|---|---|
| 드라이버 | `88x2bu`, srcversion `46A9CFB83C8F6E0C09E8AAC` |
| 드라이버 SHA-256 | `3e78ee38942e08667f68c287f0576ac21855c34cc516710de27cd49fa6137110` |
| hostapd | `ENABLED`, 5745 MHz / 채널 149, 접속 1대 |
| DHCP | 67번 충돌 후 브리지 1067/68 사용, 임대 1개 |
| 변환 | `port_only_dnat`, 요청/응답 규칙 카운터 각 2 |
| 로컬 통신 경로 | main, 정책 표 60/61 모두 wlan0 |
| CarPlay TCP | AP 주소의 IPv6 연결 1개, IPv4 연결 0개 |
| USB | 초기 부팅 약 49초에 분리/재열거, 약 52초 이후 같은 장치 번호 유지 |
| 화면 | 소유자가 CarPlay 화면 연결 성공 확인 |

0.3.0의 REDIRECT는 초기 DHCP 브로드캐스트의 목적지 IP까지 바꾸는 문제가 있었습니다. 포트만 바꾸는 DNAT로 수정했고, 이전 코드에서 실패하는 브로드캐스트 보존 회귀시험을 추가했습니다. 0.4.0에서 실제 DHCP 요청/응답과 임대가 확인됐습니다.

KP 자체 DHCP를 사용한 0.3.1 부팅도 있습니다. 이 경우 `bridge_dhcp_lease_count=0`은 브리지 파일의 값일 뿐, KP의 임대 실패를 뜻하지 않습니다. 개발판의 상태 표시와 적용 가능 여부 필드에서 이를 구분합니다.

## 미해결: 음악은 재생되지만 화면이 멈추고 반응하지 않음

화면 연결 성공을 안정화 완료로 해석하지 않습니다. 차량 소유자가 확인한 증상은 **음악 재생은 계속 정상인데 화면이 멈추고 반응하지 않는 것**입니다. 영상 전송·디코딩·화면 갱신 또는 입력 처리 경로를 우선 확인해야 하지만, 현재 자료로 어느 단계인지 특정할 수 없습니다. 음악이 계속 나오는 증상을 Wi-Fi/USB 전체 단절로 단정하지 않습니다.

소유자는 화면이 멈춰 조작할 수 없어 **직접 연결을 강제로 끊어 CarPlay를 종료했다**고 확인했습니다. 아래 세션 종료/재연결 기록을 자발적 장애의 증거로 취급하지 않습니다. 화면 멈춤의 정확한 시각은 없어 개별 로그와의 대응도 확정할 수 없습니다.

- 네이티브 진단에는 오디오의 끊김·복구 불가 패킷 집계와 전송 시간초과가 있으나, 소유자가 보고한 청취 상태는 정상입니다. 집계를 체감 오디오 장애나 화면 멈춤의 직접 원인으로 단정하지 않습니다.
- 한 세션은 약 206초 뒤 `Reason=-6753/0xFFFFE59F`로 종료됐고 다시 연결됐습니다. 사용자의 강제 종료에 따른 기록일 수 있습니다.
- Apple의 [CommonServices.h](https://github.com/apple-oss-distributions/mDNSResponder/blob/main/mDNSShared/CommonServices.h)는 `-6753`을 `kConnectionErr`로 정의합니다. 이는 연결 오류 분류이며, 그 자체로 RF 간섭·USB 고장·CPU 부족 중 하나를 특정하지 않습니다.
- 기록된 연결 종료 전후에도 AP는 ENABLED, 접속 1대, USB 장치 번호/네트워크 ifindex가 유지됐습니다. 화면 멈춤 순간을 직접 계측한 것은 아니며, 초기 부팅의 USB 재열거를 이번 멈춤의 원인으로 단정할 근거도 없습니다.
- 네이티브 세션 요약의 Wi-Fi 왕복 시간은 최소/최대/평균 2/111/10 ms였습니다. 이 집계만으로 실시간 미디어 전송의 손실·지터나 호스트 부하를 판정할 수 없습니다.
- 필터링한 기록에는 전송 오류/시간초과가 있으나, 치명적 프로세스 종료나 영상 디코더 오류를 확정하는 기록은 없습니다.

현재 결론은 **DHCP·초기 화면 연결·체감 음악 재생은 확인됐고, 화면 멈춤의 원인은 미해결**이라는 범위입니다. 강제 종료가 있었으므로 이 시험을 자연 단절/자동 재연결 안정성 시험으로 평가하지 않습니다. 마지막 저장 시점의 연결 1개는 영상 프레임이나 터치가 정상 처리됐다는 뜻도 아닙니다.

## 다음 안정화 검증

1. 화면 멈춤 시각을 기록하고, 그때 음악·차량 홈 화면·터치가 각각 동작하는지 구분합니다. 영상 전송, GPM/CarPlay 앱, 디코더/VPU/SurfaceFlinger와 입력 처리의 오류·ANR 및 부하를 같은 시각으로 대조해야 합니다. 현재의 고정 오류 필터에는 영상 프레임/디코더 진행이나 입력 처리 상태가 없습니다.
2. 멈춤 순간의 KP `perf.log`와 Wi-Fi RX/TX 오류·드롭, TCP 재전송·부하를 대조합니다. 자동 기록 수집 자체의 부하도 비교해야 합니다.
3. IPv6 미디어 경로와 IPv4/IPv6 필터 규칙을 확인합니다. 이 PR은 확인하지 않은 광범위한 ACCEPT 규칙을 추가하지 않습니다.
4. 동글 AP의 HT40/HT20 비교를 별도 차량 시험으로 수행할 수 있습니다. 현재 코드는 확인한 HT40 설정을 유지하며, 원인을 확인하지 않고 일반 차량의 채널 폭을 바꾸지 않습니다.
5. 냉간 부팅, 장시간 재생, 전화/Siri, 차량 재시작 후 자동 재연결을 반복 검증합니다.

## 호스트 시험과 한계

파일 시스템/명령 모형으로 로드 보호, 장치 선택, PID/부팅 소유권, DHCP 인계, FIFO 입력, 포트 변환, 누락 경로 보완/정리, IPv6 계수, 포트 하나 기록, 개인정보 필터를 검사합니다. C 클라이언트는 호스트에서 빌드해 실제 UNIX datagram 소켓으로 STATUS 동작을 검사합니다.

2026-11-21 로컬 검증에서 패키지 빌드, 호스트 시험 40개, bash/dash/ksh 문법 검사 42개가 통과했습니다. 배포 ZIP의 드라이버 해시·대응 소스·라이선스 포함도 검사했습니다. GitHub Actions에 동일한 빌드와 호스트 시험을 추가했습니다.

이 시험은 실제 ARM 커널·USB·무선 RF·CarPlay 렌더링을 대신하지 않습니다. 추가한 USB modalias 선택 검사는 드라이버의 `dvobj_to_dev()`/`SET_NETDEV_DEV` 소스와 확인한 `0bda:b812` 인터페이스를 바탕으로 했으나, PR 개발판 전체의 차량 재시험은 남아 있습니다. 다른 차량·펌웨어·USB ID로 검증 범위를 넓히지 않았습니다.
